# DECISIONS.md — Описание индивидуального варианта

## 1. Номер варианта

Вариант: **25**

## 2. Часть А. Изменённое правило

**Правило:** R8 — обработка дубликатов ИНН.

**Что было:** При импорте клиентов программа проверяет, существует ли уже клиент с таким ИНН. По базовому правилу R8 необходимо обработать повторную запись в соответствии с выбранным вариантом.

**Что стало:** В варианте 25 при обнаружении дубликата ИНН выбрасывается `IllegalArgumentException`. Исключение перехватывается внутри цикла, ошибка записывается в `ImportResult.errors`, а обработка следующих строк продолжается.

**Почему:** Такое поведение предотвращает повторное сохранение клиентов с одинаковым ИНН и позволяет сохранить информацию о причине отклонения записи. Обработка исключений внутри цикла обеспечивает устойчивость импорта: одна ошибочная строка не мешает загрузке остальных корректных клиентов.

## 3. Часть Б. Новый метод

**Класс:** `ClientImporter`

**Метод:** `addErrorInnList`

**Сигнатура:** `public List<String> addErrorInnList(ImportResult r)`

**Назначение:** Метод возвращает список ИНН клиентов, при обработке которых возникли ошибки. Он позволяет быстро определить проблемные записи без самостоятельного просмотра всех сообщений об ошибках.

**Код метода:**

```java
public List<String> addErrorInnList(ImportResult r) {
    if (r == null)
        throw new IllegalArgumentException("result is null");
    List<String> inns = new ArrayList<>();
    for (ImportError error : r.errors()) {
        String message = error.message();
        if (message != null && message.startsWith("ИНН [")) {
            int end = message.indexOf(']');
            if (end >= 5)
                inns.add(message.substring(5, end));
        }
    }
    return inns;
}
```

## 4. Ответы на контрольные вопросы (50–150 слов каждый)

**Вопрос 1: Какая проверка в этой работе защищает программу от наиболее вероятной ошибки входных данных и где она расположена?**

Одной из наиболее важных проверок является проверка корректности ИНН клиента. Она выполняется в классе `ClientValidator`, в методе `validate(ClientDraft d)`. Согласно правилу R3, ИНН должен состоять ровно из 10 или 12 цифр. Программа проверяет длину строки и отсутствие посторонних символов. Эта проверка необходима, потому что при заполнении CSV-файла пользователь может случайно пропустить цифру, добавить лишнюю или ввести букву. Если сохранить некорректный ИНН, в дальнейшем могут возникнуть ошибки при поиске клиентов и определении дубликатов. Поэтому при обнаружении неправильного значения программа отклоняет соответствующую запись и сохраняет описание ошибки. При этом импорт остальных строк продолжается, что обеспечивает устойчивость всей операции.

**Вопрос 2: Какой метод или класс содержит ключевое бизнес-правило и почему вы разместили его именно там?**

Ключевые правила проверки данных клиента расположены в методе `validate(ClientDraft d)` класса `ClientValidator`. Например, правило R3 определяет допустимую длину ИНН — 10 или 12 цифр, а правило R4 устанавливает требования к адресу электронной почты. Эти проверки размещены в отдельном классе, потому что валидация должна быть независима от чтения файла и сохранения данных. Класс `ClientCsvParser` отвечает за разделение строки на поля, а `ClientImporter` управляет процессом импорта и обработкой ошибок. Дополнительно правило R8, связанное с дубликатами ИНН, реализовано непосредственно в `ClientImporter`, поскольку для его выполнения необходимо обращаться к `ClientRepository`. Такое разделение обязанностей делает программу понятнее, облегчает тестирование и позволяет изменять отдельные правила без переписывания всей системы.

**Вопрос 3: Как Activity-диаграмма отражает один конкретный участок вашего кода?**

Activity-диаграмма показывает процесс пакетного импорта клиентов из CSV-файла. Блок «Разобрать CSV: проверить 3 поля, ИНН, email и дубликат ИНН» соответствует действиям, выполняемым в методе `ClientImporter.importFile(Path path)`. Сначала вызывается `ClientCsvParser.parse()`, который преобразует текстовую строку в объект `ClientDraft`. Затем `ClientValidator.validate()` проверяет правильность ИНН, имени и email. После этого программа проверяет наличие дубликата ИНН в репозитории. Если все условия выполнены, клиент сохраняется и увеличивается количество принятых записей. При обнаружении ошибки исключение перехватывается, а сообщение добавляется в `ImportResult.errors`. Стрелки возврата к чтению следующей строки показывают, что программа продолжает импорт независимо от результата обработки предыдущего клиента. Это соответствует правилам R5 и R6.

**Вопрос 4: Какое изменение требования в этой работе должно затронуть минимальное количество классов и почему?**

Примером изменения требования является изменение допустимой длины ИНН: вместо 10 или 12 цифр разрешить только 10 цифр. Для этого достаточно изменить основную проверку в методе `validate()` класса `ClientValidator`. Класс `ClientCsvParser` менять не требуется, потому что формат CSV остаётся прежним и содержит три поля. Класс `ClientImporter` также не нуждается в изменении, так как использует результат проверки валидатора независимо от конкретного правила длины ИНН. Однако потребуется скорректировать ожидаемые результаты в `SelfCheck` и тестовые записи в `data/sample.csv`, чтобы автоматические проверки соответствовали новому требованию. Таким образом, основная бизнес-логика изменяется только в одном классе. Это преимущество разделения обязанностей между компонентами программы.

## 5. Фрагмент кода для анализа

**Фрагмент:**

```java
try {
    for (String line : lines) {
        importLine(line);
    }
} catch (Exception e) {
    return;
}
```

**Проблема:** Общий блок `catch` находится снаружи цикла обработки строк, поэтому возникновение исключения при обработке одного клиента останавливает весь процесс импорта. После перехода в `catch` выполняется `return`, из-за чего оставшиеся строки файла, даже если они содержат корректные данные, не обрабатываются. Кроме того, такой подход не обеспечивает сохранение информации о каждой ошибочной записи с номером строки. Это нарушает требования R5 и R6, которые предусматривают регистрацию ошибок и продолжение импорта.

**Исправление:**

```java
int lineNumber = 1;

for (String line : lines) {
    lineNumber++;

    try {
        importLine(line);
    } catch (IllegalArgumentException e) {
        result.addError(
            new ImportError(lineNumber, e.getMessage())
        );
    }
}
```

**Объяснение:** Исправленный вариант переносит `try/catch` внутрь цикла, благодаря чему каждая строка обрабатывается независимо от остальных. Если данные клиента некорректны, исключение перехватывается, а информация об ошибке вместе с физическим номером строки сохраняется в `ImportResult.errors`. После этого программа продолжает выполнение цикла и переходит к следующей записи. Такое решение соответствует правилу R5, поскольку ошибки регистрируются, и правилу R6, поскольку ошибочная строка не прерывает импорт всего файла.
